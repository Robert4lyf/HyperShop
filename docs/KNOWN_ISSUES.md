# Known issues

| # | Area | Issue | Status |
|---|------|-------|--------|
| 1 | Env | `HYPERSHOP_ANTHROPIC_API_KEY` was not set in the Run 1 cloud container, so steps 4.5 and 4.6 could not call the API. The key was later set under that name (the `HYPERSHOP_` prefix keeps Claude Code from using it for its own auth) and both steps were run. | fixed |
| 2 | Build | Maven Central returns HTTP 429 to this container when Gradle resolves in parallel. Workaround: `--max-workers=1` and retry (verify.sh retries). | workaround |
| 3 | Build | ktlint-gradle 12.1.2, with Gradle's configuration/build caches, keeps reporting errors in deleted or renamed files. `verify.sh` runs `ktlintCheck --rerun-tasks --no-configuration-cache --no-build-cache` on its own. | workaround |
| 4 | Tests | Robolectric 4.16.1 native SQLite cannot open databases for two SDKs (34 and 36) in one test JVM (`UnsatisfiedLinkError` / `FileSystemAlreadyExistsException`). Tests that run `@Config(sdk = [34, 36])` use `@SQLiteMode(LEGACY)`. | workaround |
| 5 | Share | Step 5.9 asks for real payloads shared from Chrome, Firefox, Samsung Internet, Instagram and YouTube. There is no device here, so `SharedTextTest` uses payloads reconstructed in each app's known shape. Hand-off A checks real shares. | open |
| 6 | Tests | Room's background invalidation refresh could outlive a Robolectric test and fail the next one (`Illegal connection pointer`). Test databases run Room's query executor on the calling thread, and tests use a plain `TestApplication` (the real one opened the on-disk database and started work in every test); `AppContainerTest` opts back into the real one. | fixed |
| 7 | Keys | The Android Keystore isn't available under Robolectric, so `KeystoreApiKeyStoreTest` runs the same AES-GCM code with a plain JCA key. The real Keystore path is checked on a device (Hand-off A: enter your key). | open |
| 8 | Claude | In the eval, Claude Haiku 5.5 hit the 4000-token `max_tokens` cap on one 15-line NYT batch: it sometimes runs adaptive thinking (~1000 tokens) before a ~2000-token answer. The cap is now 16000 and the HTTP timeouts 180 s. | fixed |
| 9 | Data | `HyperShopDatabase` creates the live-key unique index `index_Item_mergeKey_live` and the `RecipeUse_kind_check_*` triggers in `onCreate`, so they are not in Room's exported schema. Nothing breaks yet (no migration exists). The first migration must drop the index before Room validates `Item` and re-create the index and triggers afterwards; so must any migration that rebuilds `Item` by copy-and-rename. | fixed: every migration extends `LiveKeyMigration`, which drops the index before the migration's own statements (so an install opened at any older version passes Room's check), and `CALLBACK.onOpen` makes it again (`MigrationTest`) |
| 10 | Claude | A call that hit the 180 s client timeout was reported as offline and its usage never recorded, though Anthropic may still bill the generation, so the spending meter could under-count. The reply is now streamed: the input tokens arrive in the first event and are recorded even if the connection then drops or stalls (the output is counted from the text received), a stall past the 60 s read timeout is reported as "Claude took too long", and the whole call has a 300 s budget. | fixed |
| 11 | Sync | The phone replied to every batch with every non-`ok` result in its 64-deep history. Under the default payload cap only about six fit a page, so once seven `noop`s had piled up (eight items ticked offline that the phone had ticked too) the pager lowered `ackedThrough` below the batch and the watch resent its last op for ever. The phone now keeps, and sends, only results the watch has not reported settled (docs/garmin-protocol.md, phone rule 2). Found in review before Run 2; `PhoneSyncModelTest` covers it. | fixed |
| 12 | Watch | The Monkey C unit tests (`garmin/test`, including the traces generated from the Kotlin model) compile in the container and against the real `fr245` definition in CI, but are only *run* by `connectiq.yml`'s simulator job (Ubuntu 22.04, Xvfb, webkit2gtk-4.0), which stays non-blocking. Release A named the hang: `monkeydo` connects, then the simulator opens a dialog over the Forerunner 245 window (titled "Error" in run 39736245866, untitled 651×132 in run 39738067898) and nothing runs for ten minutes. Installing the device fonts (`--include-fonts`, 35 fonts) did not clear it. The dialog's text is not readable from the screen grab (OCR finds only the menu bar). Next step, not taken here: dump the dialog's widget text with `xdotool`/`xprop` or AT-SPI, or run on a desktop with the SDK Manager GUI. Meanwhile the behaviour is covered on the JVM: the traces replay the same vectors through the Kotlin watch model, and `DeviceSyncVectorTest` and `WatchAcceptanceTest` run the phone side. | open |
| 13 | Import | The hybrid gate keeps the rule parser's reading when no line is flagged, so a line it misreads *without* flagging stays misread unless the user taps "Ask Claude" or edits the row: on the golden sets that is 2 % of names (`docs/reports/hybrid-gate.md`, "passed lines the rule parser still got wrong"), all of them a dropped qualifier ("packed", "block", "grated") rather than a wrong ingredient. | open (by design; the eval report is the measure) |
| 14 | Backup | A restore replaces the database in one transaction, but the settings and the ingredient-library file are written after it: a process killed in that window left the data restored with the old settings or edits. Now journalled (`RestoreJournal`, step 9.2): the file and a copy of what was there are flushed to `noBackupFilesDir` before anything is written, the next start rolls an interrupted restore forward (or back, if its copy is damaged) and says so, and a failure part-way is rolled back. `RestoreRecoveryTest` stops the restore at every stage. Verified on the JVM only; a real kill on a device is in Hand-off D. | fixed |
| 15 | Tests | The device scenarios (`app/src/androidTest`) are compiled by `tools/verify.sh`; the container has no emulator. CI's `device-tests` job runs them on an API 34 emulator. `a_quickShop`'s timeout (run 39631467809) was the test tapping the next row before the last tap had landed; it now waits for each tap's effect. After the fix the suite passed 8 times in a row across four runs (39732672436 ×3, 39734530552 ×2, 39736242502 ×1, 39738064579 ×2), with the real process-death restore check passing in the last three, and the job is now blocking. Never run them on a phone with a real list: `connectedDebugAndroidTest` uninstalls the app afterwards. | fixed |
| 16 | Performance | The first recipe search over a 300-recipe library took 2.8 s on CI's emulator (run 39738064579): it builds the search index from every line of every recipe. Later searches reuse the index, yet a second search still took 1.2 s (run 39740019670), so the index is not the whole cost. Not profiled, so not optimised on a guess; the probe measures the first and a second search separately, with budgets at about 3x (docs/reports/performance.md). On a phone with a large library it is the first thing to profile. | open |
