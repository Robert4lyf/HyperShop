# Known issues

| # | Area | Issue | Status |
|---|------|-------|--------|
| 1 | Env | `HYPERSHOP_ANTHROPIC_API_KEY` was not set in the Run 1 cloud container, so steps 4.5 and 4.6 could not call the API. The key was later set under that name (the `HYPERSHOP_` prefix keeps Claude Code from using it for its own auth) and both steps were run. | fixed |
| 2 | Build | Maven Central returns HTTP 429 to this container when Gradle resolves in parallel. Workaround: `--max-workers=1` and retry (verify.sh retries). | workaround |
| 3 | Build | ktlint-gradle 12.1.2, with Gradle's configuration/build caches, keeps reporting errors in deleted or renamed files. `verify.sh` runs `ktlintCheck --rerun-tasks --no-configuration-cache --no-build-cache` on its own. | workaround |
| 4 | Tests | Robolectric 4.16.1 native SQLite cannot open databases for two SDKs (34 and 36) in one test JVM (`UnsatisfiedLinkError` / `FileSystemAlreadyExistsException`). Tests that run `@Config(sdk = [34, 36])` use `@SQLiteMode(LEGACY)`. | workaround |
| 5 | Share | Step 5.9 asks for real payloads shared from Chrome, Firefox, Samsung Internet, Instagram and YouTube. There is no device here, so `SharedTextTest` uses payloads reconstructed in each app's known shape. Hand-off A checks real shares. | open |
| 6 | Tests | Room's background invalidation refresh could outlive a Robolectric test and fail the next one (`Illegal connection pointer`). Test databases run Room's query executor on the calling thread, and tests use a plain `TestApplication` (the real one opened the on-disk database and started work in every test); `AppContainerTest` opts back into the real one. | fixed |
| 7 | Keys | The Android Keystore isn't available under Robolectric, so `KeystoreApiKeyStoreTest` runs the same AES-GCM code with a plain JCA key. The real Keystore path is checked on a device (Hand-off A: enter your key). | open |
| 8 | Claude | In the eval, Claude Haiku 5.5 hit the 4000-token `max_tokens` cap on one 15-line NYT batch: it sometimes runs adaptive thinking (~1000 tokens) before a ~2000-token answer. The cap is now 16000 and the HTTP timeouts 180 s. | fixed |
| 9 | Data | `HyperShopDatabase` creates the live-key unique index `index_Item_mergeKey_live` and the `RecipeUse_kind_check_*` triggers in `onCreate`, so they are not in Room's exported schema. Nothing breaks yet (no migration exists). The first migration must drop the index before Room validates `Item` and re-create the index and triggers afterwards; so must any migration that rebuilds `Item` by copy-and-rename. | fixed in v2: `MIGRATION_1_2` drops the index and `CALLBACK.onOpen` makes it again (`MigrationTest`) |
| 10 | Claude | A call that hits the 180 s client timeout is reported as offline and its usage is never recorded, though Anthropic may still bill the generation, so the spending meter can under-count. A long Opus or Sonnet answer near the 16000-token cap is the likely case. Streaming the response would fix it. (Two other causes of the same under-count are fixed: leaving the review screen mid-call now cancels the request at once rather than discarding the reply after it was billed, and a reply's usage is recorded even if the caller is cancelled while it is being saved.) | open |
| 11 | Sync | The phone replied to every batch with every non-`ok` result in its 64-deep history. Under the default payload cap only about six fit a page, so once seven `noop`s had piled up (eight items ticked offline that the phone had ticked too) the pager lowered `ackedThrough` below the batch and the watch resent its last op for ever. The phone now keeps, and sends, only results the watch has not reported settled (docs/garmin-protocol.md, phone rule 2). Found in review before Run 2; `PhoneSyncModelTest` covers it. | fixed |
| 12 | Watch | The Monkey C unit tests (`garmin/test`, including the traces generated from the Kotlin model) compile in the container and against the real `fr245` definition in CI, but are only *run* by `connectiq.yml`'s simulator job (Ubuntu 22.04, Xvfb, webkit2gtk-4.0), which is experimental and non-blocking. Its first run could not connect to the simulator; it now waits up to two minutes and prints the simulator's log. The behaviour is covered on the JVM meanwhile: the traces replay the same vectors through the Kotlin watch model, and `DeviceSyncVectorTest` runs them end to end against the real phone side. | open |
